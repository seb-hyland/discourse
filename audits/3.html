audits/3.html · Discourse at e9e0e35 (seen message tracking)

Discourse audit 3

An adversarial pass over the per-comment-file design after the seen-tracking commit. Overall the storage design holds up well: adds never conflict, field-level merging handles most concurrent edits, and orphaned replies and deleted documents both get a restore. What remains is mostly at the edges: re-pinning creates conflicts the user never caused, renames strand comments, conflict resolution is only half undoable, and per-comment unread state is computed but never shown.

Fix first

  1. M1 · Deleting a thread conflicts with the other side's automatic re-pin, and the card shows two identical-looking versions.
  2. M2 · Renaming or moving a document strands all its comments under the old path; "Restore file" makes a duplicate.
  3. B1 · A draft or "Move to selection" uses offsets from text that may have changed on disk since, anchoring silently to the wrong words.
  4. B2 · Re-pinning can overwrite a comment edit saved at the same moment.
  5. S1 · Per-comment unread state (and new vs edited) is computed but has no styling; in a long thread you can't tell which comment is new.

workspace.ts:659 mergeComment() · :428 anchor comparison only when both sides kept the comment
M1 · Deleting a thread conflicts with an automatic re-pinhighreproduced

Alice deletes a thread. Bob never touches it, but edits the document, and Discourse re-pins the unpushed anchor (a write to the comment file). On merge git reports modify/delete; mergeComment sees "deleted vs changed" and asks. The card says "One side deleted this comment and the other changed it", then shows Bob's version with the same text, author and quote as before, so the user can't see what changed. The anchor-placement check at :428 only runs when both sides still have the comment.

Compare without anchor when deciding whether a side "changed" a comment: a side whose only difference from base is the anchor counts as unchanged. Delete wins silently. Generalise :428 the same way: anchors never conflict on their own; take whichever side's anchor still places, else ours, and let re-pinning tidy up.

workspace.ts:623 commentFile() keyed by document path · :358 restoreDocument()
M2 · A renamed or moved document loses its commentshighreproduced

After git mv a.md b.md, files() lists a.md as missing with one open thread and b.md with none. The only action offered is "Restore file", which writes a second copy at a.md next to b.md. Moving folders, a common refactor, orphans every comment beneath it. Branches that rename on one side and comment on the other end up the same way.

For a missing document, ask git for a rename (git log -1 --diff-filter=R --name-status -M -- a.md). If one exists, offer Move comments to b.md, which is a directory rename under .comments/; anchors still resolve, since blobs don't depend on path. Offer "Restore file" only when there's no rename.

workspace.ts:343 restoreParent() — loop breaks at the first comment with an anchor
M3 · "Restore thread" brings back only its first commentmediumreproduced

Thread root → reply1; Alice deletes the thread, Bob adds reply2. After the merge, "Restore thread" yields root → reply2. reply1, deleted in the same commit, stays gone, so Bob's reply now answers a conversation that's missing its middle.

Restore everything the deleting commit removed from that thread. That's one git show <commit>^:.comments/<doc>/ listing filtered by thread === id, and it replaces the per-comment walk.

ThreadPanel.tsx:177 folded = thread.resolved && !opened
M4 · A reply to a thread resolved elsewhere is hiddenmediumreproduced

Branch A resolves a thread; branch B adds "but wait…". The merge is clean and the thread stays resolved and folded, showing only its first comment. The new reply is visible only through the unread bar, and only if it's someone else's.

Unfold a resolved thread that has unread comments. Optionally reopen a thread when a reply newer than the resolve arrives, but that needs a resolve timestamp, so unfolding is the cheaper fix.

workspace.ts:408 conflicted ids are left out of comments · :679 missingParent() excludes conflicts
M5 · While a thread's first comment is in conflict, its whole thread disappearsmediumreproduced

With the root unreadable, toView builds no thread. Replies aren't orphans either, because their parent is "in a conflict", so they show nowhere. The document highlight goes, the file's open-thread count drops, All threads omits it, and the conflict card mentions replies only on the deleted side ("Keep it deleted, with its 3 replies"). To decide, the user has to judge the conflict without the conversation.

Render the conflict card as the thread: the replies beneath it, the highlight on whichever side's anchor places. Count it in files().

workspace.ts:326–339 resolveConflict(): this.write(…) then this.change(replies)
M6 · Settling a conflict is only partly undoablemediumby reading

The chosen version is written with write, outside undo history, and only the reply deletions go through change. After "Keep it deleted, with its 2 replies", ⌘Z brings back the two replies as orphans of a thread that's gone. "Keep this version" can't be undone at all, and the index has already been git added. No toast confirms what happened either.

Record the whole settlement as one change step, and show a "Kept Incoming · Undo" toast like delete does. Undo then rewrites the file. Whether undo should also restore the unmerged index entry is a separate question; leaving it settled is fine as long as the text comes back.

ThreadPanel.tsx:89 ConflictCard
M7 · Conflict cards don't show what differs, or offer to keep bothmediumby reading

Two long versions are rendered one after another with no diff (remaining from audit 2's M4/M8). When both sides edited the text, the only options are to drop one edit entirely. Fields that weren't in conflict (type, resolved) are shown as-is with no hint that they agree.

Show a word diff of the two texts (the diff package is already a dependency). Add "Keep both", which keeps ours and adds theirs as a reply by its author. That's a one-call add plus a settle.

workspace.ts:422–426 catch { continue; } // reported as a problem
M8 · A side that isn't valid JSON loses the side pickerlowby reading

If either stage fails to parse (a hand edit, a truncated write), the whole file falls back to "has merge conflict markers · Open in editor". The other side's version may be perfectly good.

Parse each stage on its own; offer the side(s) that parse, plus "Open in editor".

git.ts:150–155 jjSides() → "First parent" / "Second parent" / "One side" / "Other side"
M9 · jj conflicts get generic side nameslowreproduced

jj 0.44 does write index stages, so jj merges work. But the sides are "First parent / Second parent", and for a conflict that isn't a merge (a rebased commit, or a conflicted ancestor), "One side / Other side" with no commit at all. jj users identify commits by change id and description.

Label each parent by its bookmark or description (jj log -r @- -T 'bookmarks ++ " " ++ description.first_line()'). For non-merge conflicts, read jj's own conflict sides (jj file show -r @ …) instead of guessing.

workspace.ts:407 load() → merge() → write + git add, on every files()/allThreads()/search
M10 · Automatic settling is silent and runs from read-only callslowby reading

Obvious conflicts should be auto-resolved, and they are, but they're resolved inside load(), so listing files runs git add/git rm in the user's index mid-merge, with no message. Someone running git status in a terminal sees conflicts vanish on their own. If git holds index.lock right then, settle throws, and the error surfaces as the document failing to open.

Settle once per change event (see C1), outside load, ignoring a busy index. Show a one-line "Settled 3 comment conflicts automatically" toast.

2 · Seen tracking

Read state is a set of id + sha1(text) on this machine. The model is sound and survives branch switches and undo. The gaps are in what gets marked and what gets shown.

ThreadPanel.tsx:454 unseenClasses → "unseen", "new" | "edited" · styles.css has no .comment.unseen / .new / .edited
S1 · Which comment is unread is never shownhighby reading

Comments get the classes unseen new or unseen edited, but no CSS matches them. The only marks are the thread's left bar and the underline in the document. In a 10-reply thread the user can't tell which reply is new, or that the first comment was edited. The new/edited distinction (SeenStore.ids, the Unseen union) is dead code as a result.

Style .comment.unseen, for example a dot by the author plus an "edited" tag for .edited. If that's not wanted, delete ids, Unseen and unseenClasses, and make unseen a boolean.

ThreadPanel.tsx:73–82 orphans render CommentBody (no data-comment) · seenTracking.ts:34 "[data-comment].unseen"
S2 · Orphaned replies and folded comments can never be marked readmediumby reading

CommentBody has no data-comment, so the tracker never sees it. That covers orphans, the first comment of a folded resolved thread, and conflict versions. Their unread count sits in the file tree until "Mark all as read" in All threads, which also marks everything else.

Put data-comment on CommentBody. For folded threads, either count the visible first comment or unfold when unread (M4).

workspace.ts:326 resolveConflict() — no seen.mark
S3 · The version you just picked in a conflict shows as unreadlowreproduced

Bob's comment conflicts; the user reads both versions and keeps Incoming. It then shows as edited/unread, as if new. update() marks what the user wrote as read; settling a conflict should too.

this.seen.mark([{ id, text: chosen.text }]) after settling.

workspace.ts:248 markSeen(path, ids) re-reads the text from disk
S4 · Marks the text on disk as read, not the text that was on screenlowplausible

The UI sends ids; the main process hashes whatever is on disk now. If a pull or another window changes a comment within the ~1 s before marking, the new text is recorded as read though only the old one was shown.

Send { id, text } pairs, or the version hash, from the rendered CommentView.

workspace.ts:141 unseen counts loaded.comments only · FileTree.tsx:122 attention "!" replaces the count
S5 · Unread and attention compete for one badgelowby reading

Comments in conflict aren't counted as unread, and a file with any conflict, orphan or problem shows "!" instead of its count. So the files most likely to hold new activity (just merged) show the least.

Show both: the count, plus a small attention marker. Say in the tip what needs attention, for example "1 conflict to settle".

workspace.ts:582 author === this.author · seen.ts:10 "Nothing is forgotten"
S6 · Ownership by display name, and an ever-growing storelowby reading

"Mine, so read" compares the editable author string with git config user.name. Renaming yourself makes all your old comments unread; two people with the same name never see each other's. The store keeps every version ever read, forever. That's harmless for years of use, but worth one sentence in the doc comment rather than silence.

Acceptable as-is. If it matters, store the author's email as well and compare that.

seen.ts:12 "on first opening a folder, everything is [unread]"
S7 · First open of a busy repository: everything is unreadlowby design

Opening thelang for the first time shows every comment by others as unread. That's correct, but the useful "unread" signal starts out buried. The fix is a single button, and it exists, but only in All threads, behind an icon.

On first open of a folder with more than a handful of unread comments, show a toast: "142 comments you haven't read · Mark all read".

3 · Bugs and incorrect behaviour

workspace.ts:488 anchor(): only checks bounds, takes quote = text.slice(span) · App.tsx:416 onMove(span: selection!)
B1 · A draft or move can anchor to the wrong texthighby reading

The draft span is UTF-16 offsets into the text the UI had. If the file changes on disk while a comment is being written (an editor autosave, a pull), the panel re-renders with new text and the draft keeps the old offsets. The blockquote now shows different words, and on submit anchor() accepts any in-bounds span and makes the new words the quote. The comment silently lands on the wrong text. The same applies to Move to selection.

Send the selected text with the span ({ span, quote }). In anchor(), refuse with "The text changed while you were writing; select it again" if text.slice(span) ≠ quote. Better still, map the draft span through the edit in the UI when the doc refreshes, as anchors are.

workspace.ts:517–525 readOrNull(file) → await storeBlob(…) → write({ ...onDisk, anchor })
B2 · Re-pinning can overwrite a comment edit saved at the same timehighplausible

Repin reads the comment file, awaits a git hash-object process, then writes back what it read with the new anchor. Repins are triggered by the watcher whenever the document changes. A user who saves a comment edit in that window loses it: the repin writes the old text back. The race is narrow, but it's most likely exactly when someone edits the doc in their editor while replying in Discourse.

Serialise writes per document (a promise chain keyed by path covering change, repin and merge). Or re-read right before writing, after the await. The queue is the simpler guarantee.

App.tsx:218 action: { label: "Undo", run: () => void run((path) => api.undo(path, "undo")) }
B3 · Undo from the toast after navigating shows the wrong documentmediumby reading

The toast's run closes over the render where Delete was pressed, so doc.path is the old document. Delete in a.md, open b.md within 6 s, press Undo: the undo is applied to a.md (correct), but setDoc(next) puts a.md on screen while the URL hash and file tree still say b.md.

Capture path when the toast is made and call api.undo(path) directly. Only setDoc if path === shown.current?.path.

workspace.ts:562 unplaced first · workspace.ts:177 unplaced last · ThreadPanel.tsx:29 re-sorts again
B4 · Threads that can't be placed sort first in the panel, last in All threadslowby reading

toView puts unplaced threads first ("to be moved"); allThreads puts them last; the panel re-sorts open before resolved on top of toView's order. Three sorts, two orders.

Sort once in toView (open, then unplaced, then by position) and have both consumers use it as-is.

ThreadPanel.tsx:132 new Date(timestamp).toLocaleDateString() vs :332 timestamp.slice(0, 10)
B5 · The date shown and the date in the editor can differ by a daylowby reading

A comment written at 23:30−06:00 on Nov 6 shows as Nov 7 to a reader in Europe, but opening Edit shows 2026-11-06. The header converts to the viewer's zone; the editor uses the author's local date.

Display timestamp.slice(0, 10) formatted as a plain date, which also matches what update({ date }) writes.

ThreadPanel.tsx:213 current !== thread.quote && "Originally: …" · workspace.ts:524 repin overwrites quote
B6 · "Originally: …" appears or not depending on push statelowby reading

Repinning rewrites quote to the current text, so an unpushed thread never shows what it was first placed on. Once pushed, the quote is frozen and "Originally" appears after any edit. The same edit is presented differently depending on something invisible.

Pick one. The simplest is to never show "Originally" for a thread that still places (the highlight already shows where it is), and keep the quote for unplaced threads only.

Start.tsx:26 onClick={() => api.open(root)} · :37 api.choose() · :9 api.recents().then(setRecents)
B7 · Start window ignores failureslowby reading

All three promises are unhandled. open refuses folders no longer in recents without saying so (main.ts:158), so clicking a recent folder that was just deleted does nothing visible.

Have openFolder's error box cover it. In main.ts, show the "Can't open" box when the folder isn't offered instead of returning silently.

App.tsx:468 useStoredWidth · SearchPanel.tsx:271 useStoredScope, :281 useStoredHeight · AllThreads.tsx:37–46 · FileTree.tsx:34–38
Q1 · Six copies of "state backed by localStorage"medium

Each one reads a key, parses it, writes on set. The two in AllThreads are identical toggles side by side.

function useStored<T>(key: string, initial: T) {
    const [value, set] = useState<T>(() => JSON.parse(localStorage.getItem(key) ?? "null") ?? initial);
    return [value, (v: T) => (localStorage.setItem(key, JSON.stringify(v)), set(v))] as const;
}

One hook, with clamping done by callers. Saves about 40 lines.

6 · Ways to reduce overall complexity

workspace.ts load() → merge() writes · view() → repin() writes · files()/allThreads()/search all call them
C1 · Make reads pure; settle in one placebiggest win

Today every read can write: files() settles merges, view() and allThreads() re-pin, and the watcher calls view() for its side effect. This causes B2 and M10, makes the order of IPC calls matter, and is why repin needs its own on-disk recheck.

One settle(path) (merge + re-pin) run from a per-path queue on watcher events and on open; load/view/files/allThreads only read. That queue is also the lock for B2. Roughly net-zero lines, but the guard code (readOrNull/sameJson recheck in repin, busy checks in two places) shrinks.

workspace.ts:428–431 placement comparison · mergeComment anchor-as-field
C2 · Anchors shouldn't take part in conflict detection

Anchors change mechanically (re-pin) far more often than intentionally (Move to selection). Excluding anchor from mergeComment's change test fixes M1, removes the special case at :428, and loses only the rare "both sides moved the thread by hand to different places" case, where taking ours and letting the user move it again is fine.

seen.ts ids · api.ts Unseen · ThreadPanel unseenClasses
C3 · Decide on new vs edited

Either show it (S1) or make unseen a boolean and delete the ids set. As it stands, it's code with no effect.

toView sort · allThreads sort · ThreadPanel ordered
C4 · One thread order

Sort once, server-side (B4). allThreads() can then just map view().threads, and the panel can drop its re-sort.

Q1 · Q3 · Q4 · Q6 · Q7 · Q8 · Q10
C5 · Smaller cleanups

One useStored hook, one comment-file lister, one highlight vocabulary, one slide animation, one class helper, one cache. Together roughly 120–150 lines lighter with no behaviour change.
