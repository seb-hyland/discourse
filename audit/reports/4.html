Discourse audit 4

Almost everything audit 3 raised is fixed: renames move comments, re-pins no longer cause conflicts, settling is undoable and toasted, and unread comments are marked. What's left is mostly at the edges of conflict handling. The main risk: keeping the edited side of a delete-vs-edit conflict silently drops the thread's replies, and undoing a settle in a jj repository commits conflict markers. Elsewhere, any comment on a .json file puts a broken entry in the file tree, and nothing stops the window from navigating away from the app.

workspace.ts:405 resolveConflict() · :412 writes only [id, chosen] · :419 replies handled only when keeping it deleted
M1 · Keeping the edited side of a deleted thread loses its replieshighreproduced

Ada deletes a thread with two replies. Bob, on another branch, edits (or resolves) its first comment. After the merge the card says "One side deleted this comment and the other changed it". The replies merged cleanly as deleted, because Bob never touched them, so the card counts 0 replies. Choosing "Keep Incoming" brings back Bob's first comment alone. Both replies stay deleted, with no orphan card or restore offered. The user chose to keep the thread and lost most of it without being told.

When the kept version starts a thread and the other side deleted it, also bring back the replies deleted in the same commit. restoreParent already does exactly this (the sibling loop at :445–453); move that loop into a helper and call it from both. See C2.

workspace.ts:389–397 undo() writes `before`, then unsettle() · git.ts:105 unsettle() · workspace.ts:760 `before` is the file as jj materialised it
M2 · In jj, undoing a settled conflict commits conflict markershighreproduced

In a colocated jj repo, settle a comment conflict, then press Undo. Discourse writes back the file with jj's markers and restores the git index stages, so its own card comes back. But jj has already snapshotted the settled file, so the merge commit is no longer conflicted. On its next snapshot it records the marker text as the file's resolved content: jj st shows M .comments/…json and conflict is false. The commit now holds invalid JSON. The next jj command that rewrites the index drops the stages, and the card becomes "has merge conflict markers". If the user pushes first, everyone gets the broken file.

In a jj repository, don't offer to undo a settle. Leave it out of history, and leave out the Undo button on its toast. The user can still jj undo. Detect jj the same way jjSides does (no MERGE_HEAD or rebase state, and .jj present).

workspace.ts:554–558 load() picks the anchor that places in the conflicted text · :297–308 settle() writes and git-adds it · :630 repin() skips the marker-filled document
M3 · Settling a conflicted document with the other side's text unplaces its threadsmediumreproduced

A thread sits on "quick brown fox" (not yet pushed). Ada rewrites it to "slow brown fox", Bob to "quick red fox", and each side's Discourse re-pins the anchor. The merge conflicts in a.md and in the comment file. Discourse settles the comment at once, keeping Ada's anchor, because both still place inside the marker-filled text. The user then resolves a.md by taking Bob's line. The thread shows "The text here has changed too much to be sure it's the right place." Bob's anchor would have placed it exactly, but it was discarded when the comment was settled.

Don't settle a comment whose sides differ only in anchor while its document is still unmerged (unmerged(root, path) is non-empty). Settle it on the first change after the document is settled, when load's "keep the one that still places" check can see the final text.

workspace.ts:416–417 resolveConflict("both") copies author and timestamp from the other version · conflicts.ts:28 "Keeps … with … as a reply"
M4 · "Keep both" credits the other side's edit to the original author, at the original timemediumreproduced

Ada writes a comment; Ada and Bob each edit it on their own branches. "Keep both" keeps Ada's text and adds Bob's as a reply, but the reply's author is "Ada" and its date is the date of her original comment. That's because Bob's edit didn't change the author field. The reply sorts above every existing reply and reads as if Ada had answered herself before anyone else. The conflict card did name Bob, from his commit, so the information was there.

Use the side's commit author (sides[1].commit?.author, already loaded in toView) and the current time for the new reply. That's a two-line change in resolveConflict, passing the name through, or looking it up with sides().

git.ts:88 unmerged() reads only git index stages · workspace.ts:543–545 falls back to a problem
M5 · A jj conflict edited directly gets no side pickerlowreproduced

After jj rebase -r bob -d ada, running jj edit bob puts the conflicted commit in the working copy, but jj writes no index stages. Discourse sees only a file with markers: "has merge conflict markers · Open in editor". With jj new bob instead, stages exist and the full card appears. The same conflict is handled one way or the other depending on a jj habit. Remaining from audit 3's M9, which covered the non-merge case.

When .jj exists and a comment file has jj markers but no stages, read the sides with jj file show -r 'conflicts() & @', or parse jj's marker format, which jjSides already half does.

main.ts:56 void workspace.settleAll() · workspace.ts:321–323 discards each settle()'s result
M6 · Conflicts settled while the app was closed are settled silentlylowby reading

Merges made while Discourse is running get the "Settled 3 comment conflicts from the merge automatically" toast. The same merge made with the app closed is settled on open, and nothing says so. Renames found on open aren't announced either. Remaining from audit 3's M10.

Have settleAll return the summed merged and the renames. Send them as one change event, which the existing toast code then handles.

2 · Seen tracking

workspace.ts:743 commentView() · :746 unseen() — author !== this.author
S1 · Someone else's edit to your comment is never shown as unreadmediumreproduced

Bob changes Ada's comment from "Ada wrote this" to something else, and the merge is clean. In Ada's view the comment shows Bob's text under her name, with no unread mark and no file count. Ownership comes from the author field, and an edit doesn't change it. So any change to your own comments by anyone else is invisible, as is another side's version of your comment in a conflict. The same gap causes M4's misattribution.

Record who last changed the text (F1's editedBy, set in update()), and test (editedBy ?? author) !== this.author instead of author. Comments you wrote or last edited stay read on a fresh clone; anyone else's edit shows as unread.

workspace.ts:166 files() counts loaded.comments · :198 allThreads() counts thread comments · FileTree.tsx:36 · AllThreads.tsx:44
S2 · Unread counts leave out conflicts and disagree with each otherlowreproduced

Bob edits his reply on one branch and Ada edits it on hers. After the merge, Bob's version is marked unread in the card, but neither the file tree nor All threads counts it. An unread orphaned reply is the other way round: the file tree counts it, while the All threads header ("N unread comments") doesn't. So the sidebar's All threads badge and the page it opens show different numbers. Remaining from audit 3's S5.

Count once, from what toView shows: threads, orphans and conflict versions. See C1.

3 · Bugs and incorrect behaviour

main.ts:48–53 new BrowserWindow, no will-navigate handler · main.ts:67 only window.open is limited · preload.cjs:4 exposes invoke(channel) to whatever page is loaded
B1 · The window can leave the app, and the page it loads gets the IPC bridgehighplausible

Only window.open is restricted. Electron's default is to navigate when a file is dropped on the window, and nothing in the UI prevents drops. Dropping a file, say an HTML page from the repository, replaces the app with that page and leaves no way back but reload. The preload script runs for every page in the window, so that page gets window.discourse.invoke for every channel. That includes search, which reads every file in the folder, and openInEditor, which runs the configured command. The likelihood is low; the fix is one line.

window.webContents.on("will-navigate", (e) => e.preventDefault()) for folder windows and the start window. Hash changes don't fire it.

workspace.ts:811–814 commentedPaths() · :172 attention "Its comments can't be read" · :497–500 watch() maps the same way
B2 · Commenting on a .json file adds a broken "." entry to the file treemediumreproduced

Comment on package.json. The file tree gains an entry named "." with a red "!" and the tip "Its comments can't be read". readdir(…, { recursive: true }) lists the folder .comments/package.json itself, which ends in .json, so its parent "." is taken for a commented document. load(".") then fails. Any repository with comments on tsconfig.json, package.json or data files hits this.

Use readdir(dir, { recursive: true, withFileTypes: true }) and keep only isFile() entries (build the path from parentPath). In the watcher, ignore events whose type is addDir/unlinkDir under .comments (see Q5).

workspace.ts:461–470 restoreDocument() · git.ts:132 beforeDeletion() only looks for a deleting commit
B3 · "Restore file" fails for a deletion that isn't committedmediumreproduced

Delete a.md in an editor or Finder. Discourse shows "This file has been deleted. Its comments are still here" and offers "Restore file". Pressing it says "a.md isn't in the history, so it can't be restored.", although HEAD has it. Restore only works once the deletion has been committed. An accidental, uncommitted delete is the case where restoring matters most.

Try fileAt(root, "HEAD", path) first, then fall back to the deleting commit. About three lines.

7 · Ways to reduce overall complexity

workspace.ts:156–177 files() · :180–204 allThreads() · :874 issues() · :746 unseen()
C1 · One document summary for the file tree and All threads

files() and allThreads() each work out open and resolved counts, unread counts and attention from Loaded, in slightly different ways (S2, Q3). Build both from toView()'s result: open is threads not resolved; unread is the unseen comments in threads, orphans and conflict versions; attention is issues() fed with view.threads. Then the two can't disagree. It removes unseen(), the conflictedRoots special case and a second place(), about 20 lines.

workspace.ts:430–458 restoreParent() · :405 resolveConflict()
C2 · One "bring back what was deleted with it" helper

"Restore thread" (orphan) and "Keep the edited side" (M1) are the same operation: put back a thread's comments that the deleting commit removed. Pull the sibling loop out of restoreParent as deletedWith(path, threadId) and use it in both places. That fixes M1 at about zero net lines, and keeps the two behaviours from drifting apart.

workspace.ts:705–706 Conflict.thread · ThreadPanel.tsx:47 filter by thread · :52 unthreaded
C3 · Attach reply conflicts to their thread in the main process

toView returns reply conflicts in a flat list with a thread id. The panel then filters them back into threads and finds the leftovers. Put them on ThreadView.conflicts server-side, and leave in DocumentView.conflicts only those whose thread is gone. That drops Conflict.thread and two filters, about 10 lines.

8 · Feature suggestions

StoredComment (workspace.ts:67) · CommentHeader (ThreadPanel.tsx:195)
F1 · Show that a comment was edited, and by whom

Comments can be edited by anyone, and the author field stays the same. Store editedBy and edited (timestamp) in update(), and show "edited by Bob" in the header. That makes S1 visible to the user and gives M4 a correct name.

DocumentView.tsx:121–127 missing-document card
F2 · Move or delete all comments of a deleted document

When rename detection misses (a file split in two, or rewritten past git's 50 % similarity), the only options are restoring the file or deleting threads one at a time. "Move comments to…" (pick a file; anchors with an unknown base land unplaced, ready for Move to selection) and "Delete all comments" would cover it.

App.tsx keyboard handlers · AllThreads.tsx
F3 · Next and previous unread

A shortcut (for example ⌥↓ / ⌥↑) and a button that go to the next unread comment, across documents. It's the natural way to catch up after a pull, and the unread state is already there.

AllThreads.tsx:33–35 filters
F4 · Filter All threads by author and type

Types (issue, question, suggestion…) are stored and shown but can't be filtered on. "My threads", "Questions for me" and "Issues" are the obvious views for a review pass.
