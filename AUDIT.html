AUDIT.html · discourse @ 0b6394a · 2026-11-06

Discourse audit

The redesign has fixed most of the problems in the 2026-11-05 audit: per-comment files, field-wise merging, no MRSF, no HTTP server. What remains falls into three areas. Diff-based anchoring can put a highlight on the wrong text or freeze the app. Provisional re-pinning creates conflicts and writes that nobody asked for. And there is a lot of UI machinery that could be removed.

3high-severity bugs
4merge cases that behave unintuitively
~400lines of TS/CSS removable (estimate)
26/26tests pass · tsc clean

Fix first

  1. B1: when a paragraph moves, the highlight silently lands on a different paragraph.
  2. B2: an unbounded word diff runs on Electron's main process. A heavily edited document took 13.8 s and froze every window.
  3. B3: a markdown link to a .app bundle (or any file not in the list) is passed to shell.openPath, which launches it.
  4. M6: if two branches re-pin the same anchor, the user gets a conflict between two versions that look identical.
  5. M8: during a rebase, the conflict card doesn't say which version is yours.

Tags: confirmed means I reproduced it with a script against workspace.ts and real git/jj repos. plausible means I found it by reading the code. I didn't run the Electron UI, so every visual item is plausible.

1 · Bugs and incorrect behaviour

Most severe first.

workspace.ts:277 place() → anchoring.ts:28 diffEdits()
B1 · A moved paragraph takes its comment to the wrong texthighconfirmed

Pushed anchor on Para one here., then the two paragraphs were swapped. The word diff keeps Para … here. where it was and treats one/two as a replacement inside it. The thread then highlights Para two here., and the only clue is a small "Originally: …" line. That's worse than showing it unplaced, because nothing tells the user it's wrong.

Use the stored quote to verify, not to search: if the mapped text keeps less than about half of the quote's characters, show the thread as "may have moved" with Move to selection. That's about 5 lines in place().

anchoring.ts:38 diffWordsWithSpace(before, after) // in the Electron main process
B2 · A large diff freezes every windowhighconfirmed

Benchmark on a 40k-word document: 2% of words changed took 114 ms, 20% took 13,842 ms. The workspace runs in the main process, so all windows and IPC stall for that long. The edits cache only lasts one load(), so every view, refresh and comment action runs the diff again. Pushed anchors keep their old base forever, so in a long-lived, heavily rewritten document this keeps getting worse.

Pass jsdiff's timeout or maxEditLength and treat a timeout as unplaced. Cache edits by (base, currentBlob) on the Workspace. If it's still slow, run the diff in a utilityProcess.

App.tsx:152 …!files.some(f => f.path === target)) return void api.openFile(target) main.ts:100 handle("openFile") → shell.openPath(file)
B3 · A link in a reviewed document can launch an app from the repositoryhighplausible

Any relative link whose target isn't in the file list goes to shell.openPath. That includes directories, gitignored files and binaries. A link like [diagram](tools/Viewer.app) launches the bundle. Files from git clone don't get the quarantine attribute, so Gatekeeper doesn't prompt. Reviewing someone else's repository is exactly what this app is for.

Only open known-safe types (pdf, images, office documents). For everything else use shell.showItemInFolder.

anchoring.ts:15 if (edit.from <= span.from && span.to <= edit.to) return null;
B4 · Fixing a typo in a one-word anchor loses the threadmediumconfirmed

brwn → brown and colour → color both leave the thread unplaced. So does an anchor on part of the word (olou). The diff works on whole words, so any edit inside a word "replaces all of it". The design intends that only removing the text should do that.

When one word edit covers the whole span, run diffChars on just that edit's old and new text and map through the result. That's a second, local pass, about 10 lines, and needs no new library.

workspace.ts:298 storeBlob(root, content) // object exists only in this clone
B5 · A base blob that never reaches the remote leaves the thread unplaced for everyone elsemediumconfirmed

Steps: comment on uncommitted text, edit the document again with Discourse closed (so it never re-pins), commit and push. The author still sees the thread in place. A fresh clone shows it unplaced with "This text can't be found any more", which isn't true: the text is there, but the history needed to place it isn't. git add -p causes the same thing, and so does git gc pruning the loose blob after about 2 weeks.

When readBlob returns null, say so: "Placed on a version of this file that was never pushed. Ask <author> to open it in Discourse and push again." Also see §6.

workspace.ts:218 if (event === "change" …) void this.view(path) // view() → repin() → write()
B6 · Re-pinning writes tracked files during git operations and can overwrite a concurrent editmediumplausible

Every save of a commented document triggers a re-pin that rewrites comment files. That also happens while git rebase, checkout, stash pop or a jj command is changing the working tree. Writing mid-rebase can stop the next step ("local changes would be overwritten") or put the change in the wrong commit. repin also writes a whole comment object that it read before any concurrent update(), so a text edit made at the same moment as a document save can be lost.

Don't re-pin while .git/index.lock, rebase-merge/ or MERGE_HEAD exist. Re-pin only the anchor field, re-reading the file just before writing. Or remove re-pinning altogether (§6).

6 · Are blobs and offsets the right approach?

Short answer: yes, keep them. "Offsets at a fixed version, mapped through a diff to the current text" is how most review tools work: GitHub review comments (commit + line, marked "outdated" or ported), Gerrit's ported comments, Phabricator, and position mapping in ProseMirror and CodeMirror. Blob ids are a better choice than commit ids here. They're content-addressed, so they survive rebase, amend, squash and jj rewrites, and reading one is cheap. The trouble comes from three things around the core idea: word-level diffing (B1, B4), no check on the mapped result (B1), and provisional re-pinning (M6, M7, B5, B6).

How the alternatives compare

ApproachUsed byRobustnessSimplicityFits "precise, not search"?

Commit + line numberGitHub PR commentsCoarse: whole lines, and any edit to the line makes it "outdated"High✓, but too coarse for prose

Recommended changes, keeping blobs and offsets

Base = blob of the file at HEAD (or the index) where possible; no re-pinning
1 · Anchor to text that will be shared, then never rewrite the anchor

When a comment is made, map the selection from the working text to the document's blob at HEAD, using the same diffEdits in reverse. If the selected text is already committed, which is the usual case when reviewing, store that blob as the base. It's already in history, so it reaches the remote with the commit and never needs re-pinning. Only when the selection touches uncommitted text do you fall back to the working-tree blob. For that case, keep one small re-pin step that runs only at commit time, either as a pre-commit hook or when the app sees HEAD move, not on every save. That removes M6, B6 and most of B5, and anchors are only ever written when a comment is added, moved or committed.

anchoring.ts diffEdits()
2 · Diff by word, then by character inside the edit

Keep diffWordsWithSpace for alignment. When one edit covers a whole span, diff that edit's old and new text by characters (diffChars) and map through the result. That fixes typo fixes (B4) without the noisy alignment of a document-wide character diff. Add timeout to fix B2.

workspace.ts place()
3 · Check the mapped span against the quote, but never search for it

The quote is already stored. If the mapped text and the quote share less than about half of their characters, show the thread as "may have moved" rather than highlighting it (fixes B1). This stays deterministic and never searches, so it fits your decision from 2026-11-05. It turns a silent wrong answer into a visible "I'm not sure".

Optional: one-time unique-match fallback when the base blob is missing
4 · (Optional) An exact, unique quote match when the base can't be read

Only for B5's "base never pushed" case: if the quote appears exactly once in the current text, place the thread there and mark it "re-found". Anything else stays unplaced. This is a narrow exception to "no search", so it's your call. Without it, B5 needs only the clearer message from §3.

With 1–3 in place, Anchor stays { base, from, to, quote }, the stored format doesn't change, and existing thelang comments keep working.
